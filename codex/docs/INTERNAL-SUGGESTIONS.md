# 完成后出现“处理中／会话尚未命名”的修复

2026-10-19，本机日志确认两条没有写入正常聊天索引的临时 fork：20:24 和 20:58 启动，为 Codex Desktop 的输入框生成下一句建议。旧 Hook 将它们的 UserPromptSubmit 当作普通任务发给 Hub，自动优先级随即从已完成会话切到这个“处理中”的临时任务；没有名字时，原生界面显示“会话尚未命名”。这不是用户原来的任务重新执行，也不是 ESP32 掉线。

修复位于 `plugins/xueqiu-status/scripts/codex_hook.py`。不修改 Desktop 程序、Hook 定义、权限策略、真实会话优先级或设备固件。

- 对明确没有 transcript 的 SessionStart，先等待第一条实际活动再向 Hub 发布，避免后台分支初始化时先抢走完成状态。
- 仅当 UserPromptSubmit 明确没有 transcript，且带有本机已核实的“应用生成下一句建议”开头标记时，识别为内部建议任务；之后它的工具、Stop 和 SessionEnd 事件也不进入任务队列。
- 正常持久会话即使尚未命名也继续同步。真实的临时 CLI／侧聊输入继续同步；旧宿主缺少可选字段时继续按原逻辑处理。临时分支之后获得持久 transcript 时恢复正常同步。
- 私有 Hook 记录只增加事件名、transcript 是否存在、忽略原因；不保存建议提示词，不读取 transcript 文件，也不把内部任务伪装成真实会话的完成或待机事件。

官方 [Hooks 公共输入说明](https://learn.chatgpt.com/docs/hooks#common-input-fields)说明 `session_id` 与可为空的 `transcript_path`；“下一句建议”的识别来自本机当前 Desktop 日志，而不是官方对所有未来版本的承诺。未来宿主改变标记时，需要重新核对兼容性；不依靠“没有名字”进行过滤。

验证：27 项既有待答／投递测试、8 项新增 Hook→Hub 回归测试、2 项 Hook 定义检查，共 37 项通过。新增测试覆盖完成状态不被内部建议抢走、真实新任务和待答仍能切入、正常未命名会话、临时 CLI／侧聊、缺少可选元数据、跨 Hook 进程保持分类以及分支持久化后恢复。

已更新本机市场安装目录及 0.1.0–0.4.1 历史缓存中仍被聊天引用的六份脚本，保持 Hook 定义不变。当前真实会话新事件已由更新后的脚本成功投递，Hub 名称正确，蓝牙桥接仍运行。新增回归为隔离事件重放；没有为了验收额外发起 AI 对话或生成建议。
