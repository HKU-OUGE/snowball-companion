# 语音初始化与“开始录音”排错

用于实体雪球的语音初始化、布置任务、追加指令、语音回答，以及录音按钮不可用。
完整安装包的 `codex/docs/SPEECH-INPUT.md` 描述协议与使用；缓存插件目录不含完整安装器。

## 先界定能力

- 桌宠、状态同步、本地录音/识别、确认后送达是独立能力。首次设备配置应明确用户需要的范围，并逐项报告已验收或未配置。
- `install-windows.ps1` 和普通设备依赖不会安装语音模型。不要仅凭真实状态同步通过就宣布语音可用。
- 原生 Windows 的确认发送和异步问题回答使用经过身份校验的应用命名管道，见[Windows 发送前提与验收](windows-send.md)。需从当前宿主环境启动并验证工具通道，不能只安装模型就宣称任务可送达。问题回答还需准确待答 identity，不会自动批准权限。不要用模拟回执或私自发送文字代替用户确认。

## 检查顺序

1. 确认症状：按钮不可点击/语音服务未就绪、麦克风启动失败、上传失败、识别失败、送达失败分别处理。
2. 保持现有 Hub 和 BLE 连接，核对 `~/.config/xueqiu/speech.json` 是否存在；只报告配置中的 Python 和模型路径及其存在性，不打印令牌。
3. 核对配置的解释器、模型 `model.bin` 及配套 tokenizer/config 文件。检查 `127.0.0.1:4191/v1/health`，使用现有 `hub-token` 认证，要求 HTTP 200 且 `ready=true`。端口开放不等于模型加载成功。
4. 服务未就绪时，桥接器会向设备续发不可录音状态，因此该症状首先指向电脑端，不能据此认定麦克风损坏。

## 补装与启动

用户要求语音或修复该功能时，在固定保存的完整包 `codex/` 中执行：

```powershell
python -X utf8 companion/setup-speech.py
```

安装器创建独立 `~/.cache/xueqiu/speech-venv`，下载固定 revision 的多语言模型，写入私有 `speech.json` 并尝试启动 worker；不需要云端 API 密钥。下载可能较久，区分依赖安装完成、模型下载完成和服务就绪，不在模型缺失时宣布成功。

安装脚本使用宿主系统对应的解释器路径，不能把 Linux 的 `bin/python` 套到 Windows。
失败先保留具体错误，检查模型下载进度、网络和 worker 日志；不反复重配蓝牙或重启 Codex。
模型下载停滞时核对实际传输，不根据一个零字节 `.incomplete` 文件推断成功。替代下载须保持原模型与 revision，并核验完整性。

当前桥接器在语音特征首次附着时尝试启动 worker，随后约每 5 秒检查健康并续发就绪租约。
补装后先验证健康端点，再等待桥接器刷新；通常不需要重启桥接器。
若需手动启动，用配置中的解释器运行完整包的 `companion/speech_service.py --config <speech.json>`。
Windows 后台启动应隐藏窗口并将输出保存到私有日志，先检查端口和进程，避免重复 worker。

## 验收与隐私

- 检查 `~/.local/state/xueqiu/speech/service.log`；Windows BLE 日志在 `~/.local/state/xueqiu/windows/bridge.log`，其他启动方式按实际日志位置核对。
- 健康端点通过后，请用户退出并重新进入录音页试录一句。设备出现“说完了”才证明已进入录音；文字预览才证明上传和识别成功。
- 用户明确确认发送后才核对 Hub 与目标聊天的送达回执。投递结果未知时不自动重发。
- 若当前宿主返回通道不可用，明确报告“录音/识别可用，任务送达不可用”，不能声称端到端通过；Windows 需分别检查命名管道和准确问题的回答回执。
- 不记录录音或转写正文到诊断报告，不输出 Hub token、配对密钥；不把私有状态提交到仓库。
